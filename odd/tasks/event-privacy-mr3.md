# MR3 — Visibility persistence and scoped HTTP authorization
Scope: Add default-public event visibility persistence and enforce the current scoped HTTP policy only; base `1ae06079decc4af4d31d18d4dee3fa565d00b23c`, branch `feat/event-privacy-visibility`.
Risk: item 1 (additive database migration/backfill), item 2 (security: event visibility and authorization), item 3 (shared player/quiz-answer handlers also serve legacy routes), and item 5 (Docker build/deployment path needed for manual verification); no supported admin write may activate private visibility before the later protections are complete.

## Specs
S1. Issue #108 goal: “Add public/private event visibility with account-linked invited guests, separate from administrative collaborators, while preserving public-event behavior.” This MR introduces the visibility foundation while preserving the existing public-event default.
S2. Issue #108 Delivery 1: “Default-public event visibility persistence and validated owner/collaborator settings.” For this approved slice, implement default-public persistence only; defer any usable visibility-setting write API/UI until final activation after the remaining protections.
S3. Issue #108 Delivery 1: “Scoped and legacy HTTP authorization, safe metadata, record isolation and bounded legacy administration.” This MR covers current event-scoped HTTP routes and safe scoped responses/record isolation only; legacy routes and legacy administration are a separate later MR.
S4. Approved eight-MR sequence (Engram decision observation 1156): “visibility persistence/current-policy scoped HTTP”; later units separately cover legacy API/admin enforcement, WebSocket protections, media/cache protections, and “final admin visibility activation and login/return/denial UX.” Do not expand this MR into those later units.
S5. Approved activation boundary (Engram decision observation 1156): “Do not enable private through any supported admin write until scoped/legacy/WS/media protection is complete.” Events remain public by default, and this MR must not add an admin route or UI capable of switching one to private.
S6. Issue #108 guest authorization acceptance (also recorded in MR2 S3): “Invited guests may read/play but cannot administer; owners/collaborators retain administration.” Private scoped reads must recognize an accepted guest membership without granting that guest administrative access; retain the existing public access behavior for public events.
